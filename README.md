# Практическая работа №7-8
## Применение шифрования и защита информации в облачных сервисах

---

## Архитектура проекта

Реализовано мини-облачное хранилище на базе Flask с MVC-структурой:

```
cloud/
├── server.py                     ← точка входа, порт 5002, HTTPS
├── config.py                     ← конфигурация путей и ключей
├── extensions.py                 ← rate limiter
├── models/database.py            ← Model: SQLite (cloud_users, files), аудит-лог
├── services/
│   ├── encryption.py             ← Fernet, RSA, SHA-256
│   └── auth.py                   ← JWT, декораторы доступа
└── controllers/
    ├── auth_controller.py        ← /register, /login
    ├── files_controller.py       ← /upload, /download/<id>, /files
    └── admin_controller.py       ← /admin/files, /admin/users, /admin/logs
```

```
Client App ──Encrypted File──► Cloud API ──► services/encryption.py (Fernet + RSA)
                                         ──► services/auth.py       (JWT + RBAC)
                                         ──► models/database.py     (SQLite + Audit)
                                         ──► cloud_storage/         (зашифрованные файлы)
```

---

## Этап 1 — Развертывание облачного API

Был создан Flask API с тремя основными маршрутами: `POST /upload`, `GET /download/<file_id>` и `POST /login`. При обращении к серверу по адресу `https://localhost:5002/login` клиент получает точку входа в систему. Все маршруты возвращают JSON-ответы. При первом запуске сервер автоматически создаёт папку `cloud_storage/` для хранения зашифрованных файлов и инициализирует базу данных `cloud.db`.

---

## Этап 2 — Симметричное шифрование файлов (Fernet/AES)

Пользователь загрузил текстовый файл `document.txt` через `POST /upload`. Сервер прочитал содержимое файла как байты, зашифровал его алгоритмом Fernet (AES-128-CBC + HMAC-SHA256) и сохранил на диск под именем `<uuid>.enc`:

```
Оригинал:    48 байт  → "secret document content\nowner: user@cloud.local"
Зашифровано: 140 байт → gAAAAABpxFmTmEGzS32dIN9v49GoAI10w_0qklYTaJBOorrRlwC92UqJEcM-qUYG3llA3_TkqtQYNcKs...
```

Файл `document.txt` на диске в папке `cloud_storage/` содержит только зашифрованный токен — прочитать его напрямую невозможно.

---

## Этап 3 — Управление ключами

При первом запуске сервер автоматически создал симметричный Fernet-ключ и сохранил его в файл `cloud/keys/key.key`. Ключ не хранится в исходном коде — он загружается при старте приложения функцией `setup_keys()`. Файл `key.key` содержит случайные 32 байта в base64-кодировке. В реальном развертывании этот файл должен быть защищён от посторонних (права доступа 600, не добавляется в git).

---

## Этап 4 — Асимметричное шифрование RSA (гибридная схема)

Сервер при первом запуске сгенерировал RSA-4096 пару ключей (`private.pem`, `public.pem`). Реализована гибридная схема шифрования:

```
Файл → Fernet (уникальный ключ на файл) → зашифрованный файл на диске
                ↓
         Fernet-ключ → RSA-4096 (публичный ключ) → зашифрованный ключ в БД
```

При загрузке файла для него генерируется уникальный Fernet-ключ (например, `wwcJglNtPUmXKSA8ulGmGoW8n3ZFhCGjBd6006Eexfg=`). Этот ключ шифруется RSA публичным ключом с padding OAEP-SHA256 и сохраняется в поле `encrypted_key` таблицы `files` как 512-байтовый BLOB. При скачивании приватный RSA-ключ расшифровывает Fernet-ключ, которым затем расшифровывается сам файл.

Гибридная схема эффективнее чистого RSA, потому что RSA-4096 может зашифровать не более 446 байт, а Fernet без ограничений работает с файлами любого размера.

## Этап 5 — Контроль доступа (JWT)

Пользователь отправил POST-запрос на `/login` с данными:

```json
{ "email": "user@cloud.local", "password": "user123" }
```

Сервер проверил пароль через bcrypt и вернул JWT-токен:

```json
{ "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJlbWFpbCI6InVzZXJAY2xvdWQubG9jYWwiLCJyb2xlIjoidXNlciIsImV4cCI6MTc3NDQ3OTI2N30.H3n7KCEyaM66o66nGEwlfGeaHNi455Ns7UZdumGTLOQ", "role": "user" }
```

Токен содержит email, роль и срок жизни 1 час (подписан HS256). При каждом запросе к `/upload`, `/download` и `/files` декоратор `@require_auth` извлекает токен из заголовка `Authorization: Bearer <token>`, проверяет подпись и срок действия.

---

## Этап 6 — Шифрование при передаче (TLS)

Сервер запущен с параметром `ssl_context=('cert.pem', 'key.pem')` — используется тот же самоподписанный сертификат RSA-4096, что и в практической работе №6. Все данные между клиентом и сервером передаются в зашифрованном виде по HTTPS. Подключение по plain HTTP на порт 5002 невозможно.

## Этап 8 — Моделирование атак

### Атака 1: Прямое открытие файла из папки хранения

Файл `cloud_storage/507cf14b-6e47-4609-b60a-2358d027a911.enc` был открыт напрямую. Содержимое файла — Fernet-токен (зашифрованные байты). Прочитать исходный текст невозможно: данные остаются зашифрованными даже при полном доступе к файловой системе.

### Атака 2: Скачивание без JWT

На эндпоинт `/download/<file_id>` был отправлен GET-запрос без заголовка авторизации:

```
GET /download/507cf14b-6e47-4609-b60a-2358d027a911
→ 401 Unauthorized
{ "error": "Требуется авторизация" }
```

Событие `token_missing` записано в `cloud_audit.log`.

### Атака 3: Изменённый токен

Последние символы валидного JWT-токена были заменены вручную (`...GTLOQ` → `...XXXXX`), после чего токен отправлен в заголовке:

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJlbWFpbCI6InVzZXJAY2xvdWQubG9jYWwi...XXXXX
→ 401 Unauthorized
{ "error": "Невалидный токен" }
```

Подпись JWT не совпала — декоратор `@require_auth` отклонил запрос. Событие `token_invalid` записано в лог.

## Этап 9 — Облачная модель доступа (RBAC)

### Роль user — только свои файлы

Пользователь `user@cloud.local` попытался скачать файл, загруженный пользователем `admin@cloud.local`:

```
GET /download/77a5953c-81f6-4c14-ac87-f8436b86e9b3  (с токеном user@cloud.local)
→ 403 Forbidden
{ "error": "Нет доступа к этому файлу" }
```

### Роль admin — полный доступ

Администратор `admin@cloud.local` запросил список всех файлов:

```
GET /admin/files  (с токеном admin@cloud.local)
→ 200 OK
{ "files": [...], "count": 2 }
```

Администратор видит файлы всех пользователей; обычный пользователь через `GET /files` видит только свои.

## Этап 10 — Дополнительное усложнение

### Ограничение размера файла (10 МБ)

При попытке загрузить файл размером более 10 МБ Flask автоматически возвращает `413 Request Entity Too Large` — через `app.config['MAX_CONTENT_LENGTH']`.

### Rate Limiting

На эндпоинт `/upload` установлено ограничение 20 запросов в минуту с одного IP. При превышении сервер возвращает `429 Too Many Requests`.

### SHA-256 для проверки целостности

При каждой загрузке вычисляется SHA-256 хеш исходного файла и сохраняется в БД. Например, для `document.txt`:

```
sha256 = "19110e02c332fbfc9b579c0e6069dcc2a01c0f745880631816a187f7729ad4e4"
```

При скачивании хеш расшифрованного файла сверяется с сохранённым — если они не совпадают, сервер возвращает `500` с сообщением `"Нарушена целостность файла"`.

### Автоудаление файлов через 24 часа

Хук `before_request` запускает `purge_old_files()` не чаще раза в час. Функция удаляет записи из БД и файлы с диска, у которых `uploaded_at` старше 24 часов. Факт удаления фиксируется в `cloud_audit.log`.

## Контрольные вопросы

**1. Почему гибридное шифрование эффективнее чистого RSA?**
RSA-4096 ограничен в размере шифруемых данных (446 байт при OAEP-SHA256), работает медленно и не подходит для больших файлов. Гибридная схема использует RSA только для защиты короткого симметричного ключа, а сам файл шифруется быстрым AES (Fernet), что даёт скорость симметричного шифрования и безопасность асимметричного управления ключами.

**2. Что произойдёт при компрометации AES-ключа?**
Злоумышленник сможет расшифровать только тот файл, Fernet-ключ которого был скомпрометирован — поскольку каждый файл имеет уникальный ключ. Остальные файлы остаются защищёнными. Это принцип forward secrecy на уровне файлов.

**3. Почему нельзя хранить ключи в коде?**
Исходный код хранится в репозиториях (git), передаётся разработчикам, попадает в логи. Жёстко заданный ключ в коде означает, что все, кто видит код, могут расшифровать все данные. Ключи должны храниться отдельно и управляться через переменные окружения или специализированные хранилища (AWS KMS, HashiCorp Vault).

**4. Чем отличается шифрование "в покое" и "в транзите"?**
Шифрование в покое (at rest) защищает данные, хранящиеся на диске или в базе данных — в проекте это Fernet-шифрование файлов в `cloud_storage/`. Шифрование в транзите (in transit) защищает данные во время передачи по сети — в проекте это TLS/HTTPS (сертификат cert.pem). Оба вида необходимы: без шифрования в покое скомпрометированный сервер раскроет все файлы; без шифрования в транзите данные перехватываются на сетевом уровне.

## Вывод

В ходе практической работы было создано мини-облачное хранилище с полным циклом защиты данных. Реализована гибридная схема шифрования (Fernet/AES + RSA-4096), при которой каждый файл шифруется уникальным ключом, а сам ключ защищён асимметричным шифрованием. JWT-авторизация с ролевой моделью (user/admin) обеспечивает контроль доступа: пользователь работает только со своими файлами, администратор — со всеми. TLS-соединение защищает данные при передаче. Аудит-лог фиксирует все операции — загрузку, скачивание, неудачные попытки входа и ошибки токенов. Проверка целостности через SHA-256 защищает от незаметного изменения файлов на диске. Смоделированные атаки (прямой доступ к файлам, запрос без токена, изменение токена) подтвердили работоспособность всех уровней защиты.
