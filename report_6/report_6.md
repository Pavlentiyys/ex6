# Практическая работа №6
## Защита персональных данных в сети Интернет

---

## Архитектура приложения

Приложение построено по MVC на базе Flask:

```
project/
├── server.py                     ← точка входа, фабрика Flask-приложения
├── config.py                     ← конфигурация (ключи, БД, Fernet)
├── extensions.py                 ← Flask-расширения (rate limiter)
├── models/
│   └── database.py               ← Model: работа с SQLite, логирование, очистка
├── services/
│   ├── security.py               ← хеширование, шифрование, санитизация
│   └── auth.py                   ← JWT, декораторы авторизации
└── controllers/
    ├── auth_controller.py        ← View+Controller: /register, /login, /profile
    ├── admin_controller.py       ← View+Controller: /admin/*
    └── test_controller.py        ← View+Controller: /test/*
```

```
Client Browser ──HTTPS──► Flask Server ──► services/security.py (Fernet, bcrypt, SHA-256)
                                      ──► services/auth.py      (JWT, RBAC)
                                      ──► models/database.py    (SQLite, access.log)
```

## Этап 1 — Минимизация данных

Пользователь зарегистрировался, отправив на сервер следующие данные:

```json
{
  "email": "ivanov@example.com",
  "password": "MySecret123",
  "iin": "900101350123",
  "phone": "+7 701 234 56 78"
}
```

Сервер принял запрос, немедленно вычислил SHA-256 хеш ИИН и сохранил в базу только его — без оригинального значения:

```
iin_hash = "29e0f251e3cb7eabd2e26793d30f75ac8012727eafbb4915aef46b24fcbec436"  ← хранится в БД
900101350123                                                                    ← нигде не сохраняется
```

Сервер вернул ответ `201 Created`:

```json
{ "status": "registered", "message": "Пользователь ivanov@example.com успешно зарегистрирован" }
```

---

## Этап 2 — Защита пароля (bcrypt)

При той же регистрации пароль `MySecret123` был передан в функцию bcrypt с автоматически сгенерированной солью. В таблице `users` поле `password_hash` хранит бинарный BLOB вида:

```
$2b$12$HRqKpcZK2ETLGG9HN06Ag.U4arlxxWH.mgKZd2sNFPitOY.HNSbO2
```

Когда пользователь впоследствии вошёл в систему с теми же данными, сервер не сравнивал пароли напрямую, а проверял хеш через `bcrypt.checkpw`. Оригинальный пароль нигде не хранится и не передаётся повторно.

---

## Этап 3 — Шифрование чувствительных данных (Fernet)

Номер телефона `+7 701 234 56 78`, переданный при регистрации, был зашифрован алгоритмом Fernet (AES-128-CBC + HMAC-SHA256) до записи в базу. В колонке `phone_encrypted` находится зашифрованный токен:

```
gAAAAABpxFmTURCxr7xtOO0tQO-Yj4iFM2E4PCOVm6ef7jWrdf3RC_BTHrHOyNfSNNNCgoKqZ7pqw_PImulncFGIKfKKKUPsUESQFJtj_9otag6mOMAO1jQ=
```

Когда пользователь запросил свой профиль, отправив GET-запрос на `/profile` с JWT-токеном в заголовке, сервер расшифровал телефон на лету и вернул его в ответе:

```json
{
  "email": "ivanov@example.com",
  "phone": "+7 701 234 56 78",
  "role": "user",
  "created_at": "2026-03-26T01:38:00+00:00"
}
```

## Этап 4 — HTTPS

Для сервера был создан самоподписанный TLS-сертификат RSA-4096. Flask запущен с параметром `ssl_context=('cert.pem', 'key.pem')`, что означает: все данные между браузером и сервером передаются в зашифрованном виде по протоколу HTTPS.

При попытке обратиться к серверу по незащищённому HTTP-протоколу соединение не устанавливается — сервер принимает только TLS-рукопожатие. В браузере отображается предупреждение о самоподписанном сертификате (это ожидаемо для учебного стенда), после принятия которого сессия работает по зашифрованному каналу.

## Этап 5 — Контроль доступа (RBAC)

Пользователь `ivanov@example.com` с ролью `user` попытался получить список всех пользователей, обратившись к административному эндпоинту. Запрос был отправлен с корректным JWT-токеном в заголовке `Authorization: Bearer <token>`.

Декоратор `@check_role('admin')` извлёк роль из токена (`"role": "user"`) и сравнил с требуемой (`"admin"`). Роли не совпали, поэтому сервер вернул:

```
HTTP 403 Forbidden
{ "error": "Доступ запрещён" }
```

Факт попытки несанкционированного доступа был записан в лог: `DENIED:list_users`.

После того как администратор назначил пользователю `ivanov@example.com` роль `admin` через `/admin/promote`, тот же запрос вернул `200 OK` со списком всех пользователей.

## Этап 6 — Логирование доступа

Каждое обращение к персональным данным фиксировалось в файле `access.log` и в таблице `access_log`. После нескольких операций лог содержал следующее:

```
2026-03-26 01:42:11 - ACCESS | user=ivanov@example.com | action=register        | ip=127.0.0.1
2026-03-26 01:42:13 - ACCESS | user=ivanov@example.com | action=login_success   | ip=127.0.0.1
2026-03-26 01:42:15 - ACCESS | user=ivanov@example.com | action=view_profile    | ip=127.0.0.1
2026-03-26 01:42:17 - ACCESS | user=ivanov@example.com | action=DENIED:list_users | ip=127.0.0.1
2026-03-26 01:42:20 - ACCESS | user=admin@example.com  | action=admin_list_users  | ip=127.0.0.1
```

Записи доступны администратору через `/admin/logs`.

## Этап 7 — Защита от XSS

Пользователь попытался передать в поле ввода вредоносный JavaScript-код. На сервер ушли данные:

```json
{ "input": "<script>alert('XSS')</script>" }
```

Функция `sanitize_input()` применила `html.escape()` ко всем входным строкам. Сервер ответил:

```json
{
  "raw": "<script>alert('XSS')</script>",
  "sanitized": "&lt;script&gt;alert('XSS')&lt;/script&gt;",
  "protected": true
}
```

Потенциально опасные символы `<` и `>` были заменены на HTML-сущности до любой дальнейшей обработки, что исключает исполнение скрипта на стороне клиента.

## Этап 8 — Проверка уязвимостей

### SQL-инъекция

На эндпоинт `/login` были переданы данные с классическим SQL-инъекционным payload в поле email:

```json
{ "email": "admin'--", "password": "anything" }
```

Сервер обработал строку как обычный текст, передав её в параметризованный запрос:

```sql
SELECT * FROM users WHERE email = ?   -- "admin'--" воспринимается как литерал
```

Ни одна запись не была найдена, сервер вернул `401 Unauthorized`. Инъекция не сработала, структура SQL-запроса не была нарушена.

### XSS

Попытка внедрить скрипт через поле email при регистрации:

```json
{ "email": "<script>document.cookie</script>@x.com", "password": "p", "iin": "900101300123" }
```

Все специальные символы были экранированы функцией `sanitize_input()` до обращения к базе данных. В таблицу попала строка `&lt;script&gt;document.cookie&lt;/script&gt;@x.com`, а не исполняемый код.

### Перехват данных по HTTP

При попытке установить незащищённое соединение с сервером по протоколу HTTP соединение было отклонено на уровне TLS — Flask не принимает plain-text подключения при включённом `ssl_context`. Все передаваемые данные видны снифферу только как зашифрованный TLS-трафик.

### Доступ без роли admin

Запрос к `/admin/users` с токеном обычного пользователя возвратил `403 Forbidden` — декоратор `check_role('admin')` отклонил запрос ещё до выполнения функции-обработчика.

## Дополнительные задания

### JWT-аутентификация

После успешного входа сервер сформировал JWT-токен, содержащий email пользователя, его роль и время истечения (1 час). Токен подписан алгоритмом HS256. При каждом защищённом запросе декоратор `require_auth` или `check_role` проверяет подпись и срок действия токена без обращения к базе данных.

### Автоудаление данных через 30 дней

Перед каждым запросом срабатывает хук `maybe_purge`, который не чаще одного раза в час выполняет запрос `DELETE FROM users WHERE created_at < <дата 30 дней назад>`. Каждое удаление фиксируется в `access.log`. Это реализует принцип минимального хранения персональных данных.

### Rate Limiting

На эндпоинт `/login` установлено ограничение — не более 5 запросов в минуту с одного IP-адреса. При шестой попытке сервер возвращает `429 Too Many Requests`, что защищает от автоматизированного перебора паролей.

## Вывод

В ходе работы было создано Flask-приложение с MVC-архитектурой, реализующее восемь уровней защиты персональных данных. Применение SHA-256 для ИИН и bcrypt для паролей исключает возможность восстановления исходных данных при утечке базы. Симметричное шифрование Fernet защищает номера телефонов при хранении, а HTTPS обеспечивает конфиденциальность при передаче. Система RBAC на основе JWT предотвращает несанкционированный доступ к административным функциям. Проверка уязвимостей подтвердила устойчивость приложения к SQL-инъекциям (параметризованные запросы) и XSS-атакам (экранирование через `html.escape`). Дополнительно реализованы JWT-аутентификация, автоматическое удаление устаревших данных и защита от перебора паролей через rate limiting.
